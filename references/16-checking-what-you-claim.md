# 16 Checking what you claim

Part of the `coding-strategy` skill - routing table in [SKILL.md](../SKILL.md).

A document, a built package and a moved file all make claims that go stale silently.
These are the checks that catch them. Proving the code works is
[14](14-writing-tests.md); explaining it is [21](21-documenting.md); numbers have
their own failure modes and are [17](17-numbers-you-can-publish.md).

**Rules**

- If you ship an artifact, one test builds it and asserts the invariant there, and fails when the build tool is missing (16.1)
- A generated file carries a generator-written header, and a check asserts it (16.2)
- A move is proved by round-trip against the pinned pre-move commit; an in-place remap is applied in one simultaneous pass and proved by sampling pointers against the content they name (16.3, 16.4)
- Make doc drift fail mechanically; the tagged version has a changelog entry, asserted (16.5, 16.6)
- Prefer citing the band to writing an exact count or byte figure into prose; a figure you keep needs a check against the tree (16.7)
- Check done against the plan item by item, UNVERIFIABLE over DONE when unsure; every changed file the plan did not name gets a reason or a revert; acceptance text edited in the same diff to match the delivery is itself a finding (16.8)
- After a rename or removal, grep the whole tree for the old value, heavy-tier tests included, and repoint negative assertions (16.9)

### 16.1 Your checks read the tree; your users get the artifact

Every check in
[14](14-writing-tests.md) asserts over the working tree, so all of them can be green on a repo that ships a broken
package. If the project distributes anything, at least one test builds it and asserts
the invariant *in the built artifact* - a hand-maintained include list sitting beside
a generated file set is the specific thing to test. Make that test fail when the build
tool is missing rather than skip: a gate that goes green because it could not run is
the shape this file spends the rest of its length warning about.

### 16.2 A generated file says so, in the file

Anything derived carries a header the
generator writes - "generated by X from Y, do not edit" - plus a check that the header is
present in every output. Do not keep a hand-maintained table of which files are authored
and which are derived: the generator already encodes that, so the table is a second map of
the same territory and will disagree with reality first.

### 16.3 A move is proved by round-trip, not by review

When a change relocates content
rather than changing it - constants extracted to a data file, a monolith split, docs
reorganised - the source of truth is destroyed by the very commit you are trying to
verify, and the regression test [14.4](14-writing-tests.md) asks for cannot exist, because nothing about the
behaviour changed. Pin the pre-move commit, re-derive the artifact from it, and
byte-compare; enumerate the intended differences as an allowlist and fail anything
else. Pin an immutable SHA rather than following HEAD: once the extraction lands,
HEAD holds calls where the literals used to be, so HEAD cannot answer the question.
When the move fans out into variants, compare each against **its own predecessor** -
a content drop that hits one variant is invisible when every variant is checked
against a single reference. Two costs to accept deliberately: the validator needs
full history, and it must fail rather than skip when the pinned commit is
unfetchable, or it becomes the green-by-default check this file warns about.

### 16.4 An in-place remap is proved by sampling, not by a green suite

A change that rewrites
an addressing scheme where it stands - section numbers, issue IDs, route names, database
keys - leaves every pointer resolving, because the remap handed each one a valid new
target. The checks that exist to catch stale pointers go vacuous at the moment you most
need them: they assert that the target *exists*, never that it is the one meant. The
round-trip above cannot stand in either, because here the bytes are supposed to differ.
Four things do the work instead. **Survey the citation forms out of the corpus** rather
than listing the ones you remember - a form the pass misses becomes a pointer that
resolves and names something else, which is the worst defect this class produces.
**Apply the map in one simultaneous pass**: a remap is rarely monotonic, and sequential
replacement double-applies silently. **Rehearse on a copy**, and confirm there that the
guards bite before you trust them here. Then **read a sample of pointers against the
content they name** - the only step that separates a correct remap from a plausible one,
and the step a green suite will talk you out of taking.

### 16.5 Make documentation drift fail mechanically

When you find drift, prefer a check
that fails over a correction that will drift again. Documentation-truth tests assert
that documented counts match what exists, that every `file.py:NNN` reference in a
context doc resolves, that a generated reference matches its source, and that a
cited path is tracked by version control. Adding one test to one project changed a
documented number in six files - a check tells you which six.

### 16.6 The version being tagged has an entry in the changelog

Read the version, grep
the changelog for a heading naming it, fail if absent. Keep it here and not in the
release procedure, because the point is that it runs whether or not anyone remembers
the procedure. One project with a version-consistency script and 539 tests could
still bump every version file, tag, push and pass every gate with no entry, because
its doc-truth suite exempted the changelog as a historical record.

### 16.7 A number written into prose is a claim nothing reads back

Byte counts, file
counts, item counts rot at the first edit - often the edit that wrote them. One
project recorded two file sizes in the commit that created those files; `git show` of
that commit gives different numbers, so they were wrong on arrival, and the size check
already knew both. Two fixes, not equal: parse `<path> (N,NNNB)` out of the docs and
diff against `wc -c`, or stop writing the figure and cite the band the reader needs -
"over the advisory line". Prefer the second. It removes the need for a check instead
of adding one, and a claim that is not made cannot drift. Update a figure by hand, never by a
file-wide replace: that also rewrites the same number where it is history - a test id, an old
release row.

### 16.8 "Done" is checked against the plan, item by item

Mark each item the plan promised
DONE, PARTIAL, NOT DONE, CHANGED or UNVERIFIABLE, with the evidence for each. Code that
*handles* a deliverable is not the deliverable - a parser for a file is not the file. Unsure
between DONE and UNVERIFIABLE, choose UNVERIFIABLE: it costs a question, where the other costs
a missed deliverable. A PARTIAL names its cause, and one is common enough to name in advance:
the implementer's context ran out. Acceptance text edited in the same diff to match what was
delivered is itself a finding. Prior art: gstack's plan-completion review.
Then check the other direction: every file in the diff that the plan did not name is listed
with its reason, or reverted. Scope creep reads as diligence until it is counted.

### 16.9 A rename can empty a negative assertion

A test asserting the old name is *absent* passes
forever once nothing uses that name, and guards nothing from then on. For every identifier,
flag, heading or string a change renames or removes, grep the whole tree for the old value -
including tests that run only nightly or in a heavy tier - and repoint each negative assertion
at the new one. The same grep finds the half-applied rename, the more common miss.
