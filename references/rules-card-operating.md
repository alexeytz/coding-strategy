# Rules card - operating

Context docs, working in a documented repo, delegating, reviewing, running unattended,
instrumentation, debugging, sizing the ceremony and small models, in one line each - a selection,
not an index - generated by `tests/build-cards.sh` from each file's Rules block, so
edit the file, not this card. Building rules are in [rules-card.md](rules-card.md).

## 1 Sizing to the project - [01-sizing-to-the-project.md](01-sizing-to-the-project.md)

- Treat your tier's list as a ceiling, not a work order: create each item, and anything beyond it, when its absence has cost you something (1.6)
- Tier by files, domains, contributors or lifespan, whichever is highest; Tier 1 is a README, `.gitignore`, and secret scanning if it will ever be pushed (1.1–1.3)

## 5 Context docs - [05-context-docs.md](05-context-docs.md)

- The top-level doc holds what is expensive to relearn, not a description of the project (5.1)
- Under 15 files and 3 domains: no AGENTS.md; 15–49 or 3–4: root only; 50+ or 5+: hierarchy; an agent duplicating code or misplacing files: create it now (5.2)
- A child AGENTS.md defaults to purpose, ownership, local contracts, work guidance, negative constraints, verification, child index (5.5)
- List each doc in one map: a flat context index for topic docs, child indexes for child AGENTS.md files, never the same docs in both (5.7)
- The root AGENTS.md's first rule says to load the `coding-strategy` skill before the first edit (5.9)

## 6 Maintaining context docs - [06-maintaining-context-docs.md](06-maintaining-context-docs.md)

- Root context doc near 200 lines, domain doc near 300; over budget, decide: split or prune, never compress, and never evict a trap to fit (6.1)
- Run the task without the rule before adding it; re-test the rules when the model changes, and cut a safety rule only on a test with and without it (6.2, 6.3)
- An incident buys a check, not a doc paragraph; never paste a value a command could print (6.4, 6.5)
- Every addition names what it removed (6.6)
- A rewording keeps every number, condition and "unless"; diff old against new (6.7)
- A rule scoped to a file pattern gets a glob-scoped file where the runner supports one, else the nearest doc covering the pattern - never the root (6.8)
- Write a `last-verified` date only with an audit that refreshes it; staleness the audit finds is filed as debt, not fixed silently (6.9)
- Other runners' files point at the one canonical doc, and a check asserts each pointer is still there (6.10)

## 7 Working in a documented repo - [07-working-in-a-documented-repo.md](07-working-in-a-documented-repo.md)

- Before editing, read the root AGENTS.md and every AGENTS.md on the path to each target; don't rely on memory (7.1)
- The nearest doc wins on local detail; the parent wins on project-wide rules (7.1)
- After every change, do a doc pass, even when a small edit ends with no doc changed; update the nearest owning AGENTS.md when contracts, structure or workflows moved, and remove what went stale (7.2, 7.5)
- A negative constraint you would revert a commit over gets a check that asserts it (7.4)
- A doc problem noticed in passing is fixed now if cheap and open, else one line in the existing backlog - or the commit message where there is none; never a second file beside it (7.6)
- Agent-only tool output is plain text or markdown over JSON - JSON when a machine parses it too; minimal fields, deterministic order (7.7)

## 19 Instrumentation - [19-instrumentation.md](19-instrumentation.md)

- Verify instrumentation before believing it; a measurement disagreeing with the system's own health check is the suspect (19.1)
- Count by listing what you found and reading the list; gate a background waiter on its output file, never a process match (19.3, 19.4)
- Bound log inspection to the session, and stamp the entry point on a shared log (19.6, 19.7)
- A setting handed to a tool you did not write is a claim until you see it at the boundary; check every request, not one (19.8)
- A check opens what it reads read-only and must-exist, and a test asserts it wrote nothing (19.9)

## 20 Debugging - [20-debugging.md](20-debugging.md)

- No fix before the cause is located (20.1)
- Reproduce it yourself, both directions where there are two; where you can delegate, the failing test comes from an agent that has not seen the fix (20.2)
- Shrink the repro until any further cut makes it pass (20.3)
- Put a working example beside the broken one; the diff is the diagnosis (20.4)
- Trace the bad value back to where it was produced (20.5)
- One hypothesis, one edit; revert an edit that did not move the symptom (20.6)
- If it used to work, bisect what changed on a deterministic signal; call a failure pre-existing only after it fails on the base branch, and unverified when the base cannot be run (20.7, 20.8)
- Before believing a behavioural check of an edit, confirm the running process has loaded it (20.10)
- In a live incident, stop the damage before finding the cause: rollback is the operator's call, and reproduction happens off the live data (20.12)
- Fixing the code that wrote bad data does not fix the data: find what it already wrote, and repair it or record that you looked (20.11)

## 28 Delegating - [28-delegating.md](28-delegating.md)

- Every subagent is defined by name, invocation, purpose and an explicit negative constraint (28.1)
- Withhold a capability by not declaring it, keep refusal for what the caller could expect to work, and log one startup line naming what was withheld and why (28.2)
- With two agents writing at once, take a branch or worktree for anything beyond reading or a small task when you find work in progress that is not yours (28.3)
- Put every defect you found while investigating into the brief, to fix or named as left with the reason; never fence one out of scope silently (28.5)
- A hand-off whose code you will not read gets a second worker as verifier: the task is the reference, it runs things and reads the diff, the developer's report is claims (28.6)

## 29 Small models - [29-small-models.md](29-small-models.md)

- Re-run a failing task with only the relevant files; if quality returns, curate the working set, otherwise decompose or escalate (29.2)
- Hold one task to about 8 files or 10k tokens of code (29.3)

## 30 Handing work to a small model - [30-handing-work-to-a-small-model.md](30-handing-work-to-a-small-model.md)

- With a small model an assignment names exact paths, one goal and what not to touch, points at an example to imitate, and keeps discovery apart from action (30.1)
- Give the model one fast command that prints the first failure; read the installed version before calling an API, and mark what it could not check unverified rather than writing it from memory (30.2)
- Route design, cross-cutting refactors, repro-less debugging and contradictory requirements to a larger model or a human (30.3)
- The larger model writes the failing test, read-only to the small one; no test first, no split (30.4)
- Repeat a rung before climbing one; climb when the cheap rung starts producing non-findings, not when it goes quiet (30.5)

## 31 Briefing an unattended run - [31-briefing-an-unattended-run.md](31-briefing-an-unattended-run.md)

- Agree scope, autonomy, effort and what to do on failure before the operator leaves, in a table the run re-reads at its start (31.1)
- Grants are named fields in the brief that default to refusing; every step that could spend money or destroy something cites the one that allows it, and the grants that matter are also enforced where the action happens (31.2)
- Carry a budget proxy the agent can read - clock or cycles, not spend; list the one-way actions for this run (31.3)
- Ask only for what the handover did not settle - one question, then run (31.4)

## 32 Running unattended - [32-running-unattended.md](32-running-unattended.md)

- Before the first iteration and between iterations: services up, tree clean, the last run's residue at zero, the driver not the target (32.1)
- Read the report, not the exit code; every failure is a suspect, not a defect (32.2)
- Stop on a repeat failure after a documented repair, a fix needing a test changed when it is unclear which was wrong, anything outside the test namespace, a red tree, underspecified work, an ungranted one-way action, or a crossed budget (32.3)
- A behavioural change to shipped code with no mechanical oracle is `verifier-only, unconfirmed` and does not close (32.3)
- Hand back in the final message, in 32.4's order; a file only if the brief asks or the project keeps one (32.4)
- Record verdicts and corrections as the run goes: in the commit messages if it commits per iteration, else one append-only log (32.5)
- Stop when every item in the brief is done or handed back; unasked work goes in the hand-back, not the tree (32.6)

## 33 Running a review - [33-running-a-review.md](33-running-a-review.md)

- Before opening code, read whichever the project keeps of the root context doc, the trust-boundary doc and the handover's traps and settled sections; a finding contradicting one names it and says why it is out of date (33.1)
- Old findings files are leads to re-verify, never context (33.2)
- Verify before logging and quote what you read; never report an observation you did not make, and log what you cannot verify as unverified (33.3)
- An impact paragraph reaching "no practical impact" deletes the finding, unless it names a documented standard and the change the violation made harder (33.4)
- Engage with the comment, changelog or decision record explaining the behaviour before proposing a fix (33.5)
- Log a pattern once with every instance in scope; check the fix reached every surface, branch and operation (33.6)
- Scan every diff for weakened gates; one that silences its failure with nothing in the diff to justify it goes to a human - its commit message does not count (33.8)
- Trust-boundary findings go to the top of the log and are reported at once (33.9)

## 34 Findings log - [34-findings-log.md](34-findings-log.md)

- Write findings to your own file at a known path, header first, each finding appended the moment it is confirmed (34.1–34.3)
- Severity is assigned after verifying, by consequence (34.4)
- The final report says what you could not verify, what you did not examine, and what looked suspicious outside the scope (34.5)
- An empty findings file fifteen minutes in is a defect in your run, not evidence of none (34.3)
- A run that reported nothing looks like a run that found nothing: check the final-report section exists before reading the findings (34.6)

## 35 Verifying findings - [35-verifying-findings.md](35-verifying-findings.md)

- Drive every finding against the code; verify the claim, not the label; search the quoted snippet, not the cited path (35.1, 35.2)
- A refuted finding goes back to the agent that filed it (35.3)
- Unactioned findings go to a backlog headed "every line is a claim", with four exits (35.5)
- Copy findings files somewhere durable before a release deletes them (35.6)

## 36 What a round is worth - [36-what-a-round-is-worth.md](36-what-a-round-is-worth.md)

- Repeat a rung before believing a clean result from it (36.1)
- Reviewers find bad lines and miss missing ones; answer a found class with a mechanical check (36.2)
- When a review does not fit one context, split it along the axis that keeps compared things together (36.3)
- Brief a reviewer with the artifact and its contract, never your verdict (36.4)
- Docs get their own audit pass against the code; a code review does not check them (36.5)

## 37 Reference - [37-reference.md](37-reference.md)

- Look up a lesson in the anti-patterns table before repeating it (37.1)
- Language- and tool-specific patterns belong in other skills; across services, apply 2's tree per service, never once over all (37.2)
