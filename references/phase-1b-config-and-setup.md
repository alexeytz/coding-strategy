### 2. Config Split

Structural config (JSON/YAML) vs environment config (.env). Env vars always win.

- **JSON/YAML:** collections, scoring weights, feature flags — rarely changes
- **.env:** URLs, model names, paths, API keys — changes per host/environment
- Explicit priority: env vars > JSON config > hardcoded defaults
- Document all env vars with required/optional markers and defaults

**Never commit secrets.** Ship `.env.example` with placeholder values.

#### Make the resolution observable

Stating precedence is not the same as being able to see it. Three rules, each paid for:

- **Print which layer won.** For every layered value, the resolved source at startup or
  behind a flag. Without it, "why is this value 512?" is answered by reading source, and
  a layer that silently never applies looks identical to one that agrees. The payoff
  scales with the number of layers; for `.env` over a default it is overhead.
- **Keep authored and effective config as two objects**, not one merged blob — you
  cannot diff what a user set against what the system decided once they are the same
  dict.
- **The config reference is derived, not maintained.** `.env.example` listing every
  variable with REQUIRED/OPTIONAL and its default is this skill's own rule with nothing
  checking it. Where config is declared in code, generate the reference from the
  declarations and assert every field has a default and a description. Where config is
  a flat `.env` read by bare env lookups there is no declaration site, and building one
  just to enable the check inverts the cost — then keep it by hand and know it drifts.

**The layer an agent can write is the layer that loses.** Precedence cuts both ways: if
an agent writes a value into the config file while an env var sets the same key, its
write is real, persisted, and has no effect. It will not notice. Either let runtime
writes go to the layer that wins, or refuse the write and say which layer is shadowing
it.

**One process serving several configurations breaks two things quietly.** A singleton
built from the first configuration it saw, and a cache keyed without the tenant in the
key. Both return the wrong tenant's answer rather than failing. If one process serves
more than one configuration, the tenant belongs in the cache key and in the identity of
anything constructed once.

#### Dependencies

Commit the lockfile. It is the difference between "works on my machine" and a reproducible
checkout, and it is the file most likely to be regenerated by accident — an agent with a
terminal installs things, and the install rewrites it. Treat a lockfile change as a real
change: it never rides along in an unrelated commit, and an agent that regenerates one says
so rather than letting it appear in the diff. Pin direct dependencies to a range you have
actually tested and let the lockfile pin the rest exactly. Update on a schedule you choose
rather than whenever something happens to reinstall.

### 3. Externalize Configurables

Regex patterns, prompts, thresholds, entity definitions, scoring weights — store as data files, never hardcoded.

**Why:**
- Keeps code clean (no 20-line regex literals in Python)
- Users/customers can tweak without editing source
- Version-controlled alongside code
- Hot-reloadable in many cases

**Common patterns:**
- `config/patterns/*.json` — regex patterns, entity definitions
- `config/prompts/*.md` — LLM prompts, templates
- `config/defaults.yaml` — thresholds, timeouts, limits

**Convention:** ship a `default.*` file with comments. Users copy to `custom.*` to override. Never edit `default.*` directly.

#### Deterministic scripts over agent reasoning

Not just config — also procedures. Any deterministic multi-step sequence (deploy, lint + test + commit, backup + verify, environment setup) belongs in a script, not in the agent's working memory.

**Why:** Every step the agent reasons through instead of running a script costs tokens and introduces variability. A bash/Python script runs the same way every time.

**Pattern:** `scripts/<action>.sh` or `scripts/<action>.py`. The agent calls the script; the script does the work. If the script fails, the agent reads the output and decides next steps.

**Examples:**
- `scripts/deploy-staging.sh` — build, run migrations, deploy, smoke test, report status
- `scripts/setup-env.sh` — create venv, install deps, generate .env from template, validate
- `scripts/run-full-suite.sh` — lint, test, security scan, collect results into a single report

**Rule of thumb:** If a procedure has more than 3 sequential steps and the logic doesn't change between runs, it's a script, not a prompt.

#### One-Command Setup

Every project ships a single entry point that gets a fresh clone to a working state. Install dependencies, copy `.env.example` to `.env`, run initial migrations, validate the result.

**Pattern:** `scripts/setup.sh` (or `make setup`). One command, zero friction.

**Why:** New agents and human developers hit the same wall — "how do I get this running?" A single command eliminates that barrier and guarantees reproducibility.

**Minimum requirements for `setup.sh`:**
1. Install dependencies (language-specific package manager)
2. Copy `.env.example` to `.env` (abort if `.env` already exists)
3. Run initial migrations or schema creation
4. Validate: print a success message with version info

#### One verification entry point, not a table of commands

Put the verification sequence in `scripts/verify.sh` beside `scripts/setup.sh`, and have
the pre-commit hook and CI call it with no logic of their own — otherwise the same checks
drift into three spellings, and the one a contributor runs locally is not the one that
gates the merge. Gate expensive stages on an env var naming a **capability** rather than a
machine (`HAS_GPU`, not `ON_THE_BIG_BOX`), so a stage that did not run says which
capability was missing instead of silently passing. Each stage appends to a report the
script prints at the end, which is the artifact
[phase 3b §9](phase-3b-verifying.md) wants a row of. Where verification is two commands
and always runs, this is ceremony that rots faster than the two commands — it starts
paying when some stages do not always run.
